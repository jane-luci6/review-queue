Morning reset

Start the day on a known look

Every shift leaves decisions behind. A source was changed for an event. A volume was raised for a busy room. A display stayed on after the audience moved on. By morning, the floor may still reflect the night before instead of the day ahead.

Then opening becomes a negotiation with the last shift. Property A/V and operations teams have to determine what changed, what should still be running, and what needs to return to normal. The work is familiar, but it should not have to be reconstructed each day.

A morning reset in current LUCI gives the property a known starting point. One command returns the house to the state selected for open: the intended sources, display looks, audio zones, and volume levels. The reset runs from the same interface used to operate the property’s A/V.

The day starts on purpose, not on whatever last night left behind.

The property defines the open look once, based on how the floor should operate. That state becomes the reset. When the day begins, staff can call it back without rebuilding each zone or retracing the previous shift’s changes.

The move is direct: choose the preset, apply it, and the floor returns to the selected state. Displays and audio do not have to be addressed as separate jobs. The command reaches the systems already coordinated through LUCI.

This matters because opening is not the only time a known state has value. Events, promotions, and late changes can all move a room away from its standard look. A reset gives the operation a defined point to return to. It replaces guesswork with the property’s own decision about what normal should be.

The value is consistency across shifts: the opening state belongs to the property, not to whoever last touched the controls.

LUCI works with and absorbs the A/V already on the floor. It does not replace the displays, audio, sources, or control systems the property has chosen. It brings them into one operating interface, where a morning reset can act across the room instead of stopping at the boundary between systems.

A walkthrough begins with the property as it exists: its sources, zones, opening conditions, and accumulated A/V. From there, the team can see what a known opening state would include and how LUCI would call it back.

Lighting through LUCI

Lighting lives with the rest of the A/V

Lighting is often treated as a separate operation. It has its own console, its own controls, and its own place in the room. A/V lives somewhere else. When the room changes, the two systems have to be coordinated even though the guest experiences them together.

That separation adds another interface to staff and another set of actions to align. The display can change while the lighting stays behind. The audio can move into an event state while the room remains in its everyday look. Operations is left to make separate systems behave like one environment.

Current LUCI brings lighting into the same interface as displays, audio, and sources. Lighting remains the lighting system the property already has. LUCI absorbs its controls into the wider A/V operation, so staff can manage zones, levels, and looks without leaving the interface that runs the room.

The benefit is one place to operate the experience. The property does not have to treat lighting and A/V as separate events that happen to occupy the same space. The room is one room. The interface reflects that.

From LUCI, staff can change a lighting look, select a zone, or adjust a level alongside the other controls for the space. The lighting look appears as a control in LUCI, just as a source does. Staff can see it in the context of what the room is doing instead of moving to a separate console and reconstructing that context.

This is not a case for replacing the property’s lighting. It is a case for operating it with the rest of the room. LUCI works with and absorbs the lighting and A/V systems already on the floor. The fixtures, controllers, displays, audio, and sources remain in place. Their controls stop living in separate operational silos.

For A/V, IT, and operations leaders, that changes the scope of the question. It is no longer, “Who is running lighting tonight?” and “Who is running A/V?” It becomes, “What should the room do?” The answer can include the lighting look, display sources, and audio state on the interface used to run the property.

Revert preset

Try a look. Get the last one back.

A live floor leaves little room for uncertain changes. A different source, audio level, or zone layout may improve the room. But if the result is wrong, someone has to restore the last state while the property is still operating.

That is where experimentation stops. The problem is not the change itself. It is the absence of a dependable way back. If the prior state has to be remembered or rebuilt one system at a time, keeping the current look can feel safer than testing the next one.

A revert preset in current LUCI preserves the known state before the room changes. Staff can save that state, apply a new look, and assess the result. If it is not the room they wanted, they can revert. The sources, zones, levels, and other saved controls return to the prior state.

The feature is a small control with a larger operational effect. Staff can consider what the room should become without losing the state that is already working. The last look remains available while the next one is tested.

The move is direct: save the known state, apply the change, and revert if the result is not right. This is not a procedure for rebuilding the room. It is the removal of the rebuild from the decision.

For property A/V and operations teams, that means a live room does not have to be fixed in place. A new event look can be assessed. A different source arrangement can be tested. A zone can be changed for the way the room is being used. If the change does not hold up in the space, the saved state is still there.

LUCI works with and absorbs the A/V already on the floor. It does not replace the displays, audio, sources, or control systems the property uses. The revert preset acts across the controls brought into LUCI, so the return is not divided into separate jobs for separate systems.

This is what one interface makes possible: not only sending a new command, but keeping the prior operating state within reach. The property can move forward without giving up its way back.

Announcement volume

Not every announcement should be the same volume

Not every announcement has the same job. A bingo call, an emergency page, and “the buffet is open” ask for different levels of attention. When all three are delivered at the same volume, the guest-facing A/V treats them as if they carry the same weight.

The result is a false choice. Keep every announcement loud enough to cut through, and routine messages become intrusive. Keep every announcement restrained, and the messages that must take the room may not do their job. One building-wide setting cannot express the difference.

This is not a speaker problem. It is a control problem. The audio system can deliver the page, but the operation needs to determine how that page should behave.

Current LUCI assigns announcement levels by job instead of relying on one slider for the building. A routine page can have its place. An emergency page can have another. The level belongs to the announcement, much as a look belongs to a zone.

The benefit is alignment between the message and the way the property delivers it. Routine pages can remain routine. Announcements that must cut through can do so. Staff are not forced to choose one permanent level for unrelated messages.

Property A/V and operations teams can define levels around the work each announcement performs. That might mean keeping a guest update within the room it serves while allowing a critical page to reach the areas where it must be heard. The property decides the level for the job instead of asking one setting to cover every use.

The move is visible in the interface: the announcement has a level, the way a zone has a look. Staff select the announcement they need; LUCI applies the behavior the property assigned to that job.

The message determines the treatment. The building no longer has to make every announcement compete at one setting.

LUCI works with and absorbs the audio system already on the floor. It does not replace the speakers, amplifiers, paging infrastructure, or other A/V the property has selected. It gives those systems one operating interface, including control over how an announcement is scoped.

A walkthrough begins with the property’s existing zones, paging paths, and announcement jobs. From there, the team can hear how LUCI distinguishes a routine message from one that needs the building’s attention.

What you may not know

What you may not know about LUCI

The first misconception about LUCI is usually a hardware misconception. A prospect hears LUCI and assumes it means new displays, new speakers, new lighting controls, or a new stack to replace what the property already bought.

That is not what LUCI is.

The A/V stays. Displays, audio, lighting, sources, and control systems remain in place. LUCI works with and absorbs them, bringing their controls into one interface. It is how the property runs the systems together—not a replacement for the systems themselves.

That distinction changes the first conversation. If LUCI is mistaken for the stack, the discussion starts with a catalog: which displays, which speakers, which controllers, which boxes. It treats the property as an empty room waiting to be specified.

Most prospects are starting somewhere else. The room is full. The property has accumulated A/V over time, often across separate projects, interfaces, and operating paths. Each system may perform its assigned job. The problem appears when staff have to run the property as a collection of systems instead of one operation.

That is where a first look at LUCI should begin: with the property’s actual A/V. What is already on the floor? Which systems are separate? Which rooms require their own controls? Where do staff move between interfaces to complete one guest-facing change?

The purpose is not to assemble a list of new hardware. It is to see the current operation in one place, then understand what changes when its controls are consolidated. The displays remain displays. The lighting remains lighting. The audio remains audio. LUCI gives the property one interface to control, automate, and execute across them.

That does not make the underlying systems interchangeable, and it does not erase the expertise required to operate A/V. It removes the need to treat every system boundary as an operating boundary. Staff can work from a common picture of the property instead of reconstructing that picture across separate consoles.

This is what LUCI is—and what it is not. It is not the wall, the speakers, the lighting, or a demand to replace them. It is the orchestration engine that brings the A/V already in the building into one operation.

The first walkthrough should reflect that. Bring the systems already on your floor and the way your teams run them today. The conversation starts there, not with a catalog.
