# New LUCI What’s New — format strategy v2

**Revised recommendation for Jane · 17 September 2026**

**Decision status:** This memo supersedes the recommendation in `new-luci-whats-new-format-strategy.md` for decision-making. V1 remains intact as the research record, including its comparable-release table.

## The answer in one sentence

Build one simple release path around a benefit-led one-pager, then open only the doors each audience needs: direct, fulfilled upgrade communication for current customers; orientation and a guided next step for prospects; demonstration through a webinar or overview video; and PR for broader awareness.

Do **not** build a public Upgrade Guide + FAQ as the canonical detail hub. That was the central recommendation in v1, and it does not fit how LUCI is obtained, upgraded, or supported.

## Why the recommendation changes

The peer research in v1 remains useful as a record of how other companies divide announcement, reference, and demonstration. It is not a blueprint for LUCI.

Those companies often support public downloads, multiple hardware generations, self-directed trials, model comparison, version archives, or customer-administered upgrades. LUCI does not. Software is obtained after contract. Current customers receive a shipped laptop with the software. An upgrade is a one-to-one fulfillment process, not a blast that is expected to create download volume.

That changes the information problem. LUCI does not need to help an unknown visitor discover an old version, select among player SKUs, or complete an upgrade alone. It needs to:

1. Explain the value of the new version simply.
2. Tell each known customer what happens next.
3. Give prospects enough orientation to understand the single solution.
4. Provide deeper, installation-specific detail when it becomes relevant.
5. Communicate end of support intentionally to affected customers.

The communications system should reflect LUCI’s advantage: one solution in a complicated purchasing environment. A large public documentation ecosystem would import the complexity LUCI removes.

## What still holds from v1

- **Keep the one-pager.** It is the shortest complete release argument and the shared orientation asset.
- **Keep one campaign spine.** The locked theme is **Putting the power of programming in your hands**, organized under **Operate · Make it yours · See and secure**.
- **Keep detail off the one-pager.** The sheet should not become a technical catalog, setup guide, or change log.
- **Use email to route the audience.** Customers and prospects can receive the same core story with different next steps.
- **Use demonstration to make the release tangible.** A webinar or concise overview video can show the new experience better than a denser sheet.
- **Separate announcement from fulfillment.** Marketing explains why the release matters; direct customer materials explain what happens next.
- **Maintain one source for approved release facts.** All assets should draw from the same locked claims and pillar structure, even when their depth differs.

## What no longer applies

- **No public Upgrade Guide + FAQ as the canonical self-serve hub.** Customers cannot independently download or complete the upgrade, so a public archive would imply a process that does not exist.
- **No stable public upgrade URL as the required answer to every detail question.** The durable answer is a controlled, directly delivered customer release brief plus the customer’s individual fulfillment path.
- **No public compatibility, download, release-note, or version-history ecosystem modeled on peers.** Create only the information LUCI needs to fulfill the upgrade and support the account.
- **No hardware chooser modeled on BrightSign.** LUCI has one box. Additional hardware depends on the customer’s endpoints, existing technology, and situation.
- **No assumption that the webinar must sit beside a public written archive.** It can be a guided customer/prospect experience, with the right follow-up supplied directly.
- **No asset stack justified merely because peer companies have one.** Their product and distribution complexity is not evidence that LUCI needs the same volume of material.

## Revised recommendation — the LUCI-shaped information path

### The common front door

The one-pager is the common orientation piece for customers, prospects, sales, PR follow-up, and meetings. It should communicate:

1. **Theme:** Putting the power of programming in your hands
2. **Pillars:** Operate · Make it yours · See and secure
3. **Benefit-led proof:** what people gain from the new version
4. **One clear next action:** routed by context, not a generic public download

From there, the path splits once and stays simple.

### Current-customer path

**One-pager or release email → direct LUCI contact → customer-specific upgrade plan → shipped laptop and thin fulfillment materials → optional live or recorded walkthrough**

Existing customers already know how LUCI works. They do not need the full prospect orientation story or a library to search. They need a direct answer to four questions:

- What do we get from the new version?
- Does anything change for our operation?
- When are we eligible or scheduled?
- What will LUCI send, do, or need from us?

The account-specific upgrade plan is part of the answer because endpoints, existing technology, timing, and any additional hardware vary by customer. The materials should make the fulfilled process legible without pretending it is self-service.

### Prospect path

**One-pager or PR → product-page orientation / seller conversation → webinar, overview video, or guided demo → sales process**

Prospects need more context than current customers, but they still should not have to navigate a documentation stack. The product story should establish the problem, the single LUCI solution, the three release benefits, and the guided next step.

A LUCI-box image may help recognition on a product page. It should never read as a model selector or suggest multiple boxes to compare. That decision remains open.

## The job of each asset

| Asset | Primary audience | Job | It should not become |
|---|---|---|---|
| **One-pager** | Customers and prospects | State the release promise, organize the three pillars, and show what people get | Feature inventory, setup guide, hardware matrix, or upgrade instructions |
| **Email** | Separate customer and prospect sends | Put the common story in audience context and route to the right human or guided next step | One undifferentiated blast or a substitute for customer fulfillment |
| **Webinar or overview video** | Customers, prospects, or separate sessions as useful | Show the new version in use; orient, demonstrate, and answer questions | The only record of upgrade requirements or an ownerless production commitment |
| **Thin fulfillment materials** | Existing customers entering the upgrade process | Confirm what happens next, customer-specific requirements, responsibilities, timing, delivery, support route, and approved release detail | A public download archive or a broad documentation ecosystem |
| **Press release** | Market, partners, possible publications | Announce the new version through the benefit story and create credible external awareness | Customer upgrade notice, technical reference, or inflated proof vehicle |

### PR in the plan

Add a press release to the launch plan and evaluate selective publication pickup. The release should carry the theme, the three benefit pillars, and the significance of putting programming power in operators’ hands. It should not invent metrics, name clients without approval, or explain fulfillment mechanics.

Potential outlets and outreach priority remain Jane’s decision. The plan should distinguish an owned press release from earned pickup; publication is not guaranteed.

### Webinar or overview video

The Cisco-style short overview video is a strong format to consider because it can orient prospects and refresh current customers without adding reading burden. A webinar adds demonstration and Q&A. These are not automatically separate productions; the launch can choose one, sequence them, or reuse a webinar recording if that produces a clear overview.

Do not assign production or ownership yet.

## Where end-of-support communication belongs

End of support for the current LUCI should be handled as an intentional customer communication program, not as a notice buried on a public download page.

Once Jane locks the date and policy, the message should live in:

1. **Direct notices to every affected current-customer contact**
2. **The customer’s upgrade-plan or “what happens next” piece**
3. **Account follow-up and fulfillment records**, so LUCI can confirm who received the notice and what action remains
4. **Appropriate reminder communications before the deadline**, with timing set only after the policy is locked

The notice needs to state the support date, consequence of waiting, direct route to schedule the fulfilled upgrade, and what the customer should expect. It should not point to a download archive. If a customer returns years later, LUCI handles the path directly because the software still cannot be obtained online.

## One-pager craft — benefits before feature inventory

BrightSign’s useful lesson is not its hardware or documentation ecosystem. It is the order of persuasion: a short feature orientation followed by the benefits of the new version.

For LUCI, the one-pager should go further toward **what customers get out of it**:

- **Operate:** the operational result first; selected capabilities as evidence
- **Make it yours:** the control or adaptability gained first; programming features as evidence
- **See and secure:** the visibility and governance gained first; activity, access, or security capabilities as evidence

This is direction for the next copy pass, not a rewrite here. It connects to the separate one-pager approach memo and does **not** lock approach A, B, or C.

## Explicit answer — if the one-pager stays high-level, where does a customer get more detail?

**From a concise, versioned customer release brief delivered directly by LUCI, paired with a named LUCI contact, the customer-specific upgrade plan, and a live or recorded walkthrough when useful.**

That release brief is the controlled detail source for approved feature behavior and common questions. The upgrade plan adds the installation-specific answer: timing, shipped equipment, prerequisites, responsibilities, and support. The format may be a short PDF, an unlisted page, or another directly delivered piece; it is not a public self-serve hub, and the exact container should be chosen only after Jane decides how thin the customer “what happens next” piece should be.

## Decisions still Jane’s

1. **End-of-support:** date, policy, notice timing, and consequence language
2. **Overview video:** whether to make it, its role relative to a webinar, and who owns production
3. **PR:** target outlets, outreach priority, and who handles pitching
4. **Customer fulfillment piece:** how thin “what happens next” should be and whether the release brief is part of it or a paired item
5. **One-pager approach:** A, B, or C in the separate approach memo
6. **LUCI-box photo:** whether it belongs on a product page for recognition only

## Recommended lock

Lock the communications architecture as:

**One common, benefit-led release story → a direct fulfilled path for customers → a guided orientation path for prospects → optional demonstration → PR for awareness.**

Do not create the public Upgrade Guide + FAQ proposed in v1. Keep the system deliberately small, make every next step self-explanatory, and add detail only where LUCI’s contract-led, customer-specific process requires it.
